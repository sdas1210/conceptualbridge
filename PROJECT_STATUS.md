# 2. API Architecture Clarification

Two existing APIs have been distinguished and must not be treated as identical.

## `api/fetch-questions.js`

Primary role:

**Exam Corner / general dynamic question retrieval**

Current behavior is anchor-independent.

It accepts criteria such as:

```text
topic
limit
```

and can discover questions across the appropriate subject/question folders.

Conceptually:

```text
Exam Corner
    ↓
fetch-questions.js
    ↓
Subject / Topic criteria
    ↓
Multiple eligible question files
    ↓
Question selection
```

This endpoint should **not simply be replaced by `runtimeEngine.js`**.

`runtimeEngine.js` is the Runtime execution layer, while `fetch-questions.js` is an API entry point.

---

## `api/fetch-tutorial-questions.js`

Primary role:

**Tutorial Corner / anchor-driven question retrieval**

Current architecture is source-specific and accepts a specific source file.

Conceptually:

```text
Tutorial Corner
    ↓
fetch-tutorial-questions.js
    ↓
Specific source
    ↓
One TXT question file
    ↓
Select 10 questions
```

### Intended Future Rule

Tutorial Corner is intended to become **strictly Anchor-driven**.

The Anchor is the authority for the Tutorial flow.

If:

```text
Topic|
Sub-Topic|
Level|
```

are blank, the Runtime should follow the Anchor/Test_Source strictly.

If one or more of these metadata fields are supplied, they become filters within the Anchor's permitted source scope.

Example:

```text
Test_Source| questions/gaca/1.txt
Topic|
Sub-Topic|
Level|
```

means:

```text
Strictly use questions/gaca/1.txt
→ eligible questions
→ select 10
```

Whereas:

```text
Test_Source| questions/gaca/1.txt
Topic| History
Sub-Topic| Ancient India
Level| 10
```

means:

```text
Anchor source = questions/gaca/1.txt
        +
Topic = History
        +
Sub-Topic = Ancient India
        +
Level = 10
        ↓
Eligible questions
        ↓
Select 10
```

### Architectural Principle

The Anchor remains the **authority / scope definition**.

The Knowledge Index is a **fast lookup/index layer**, not a replacement for the Anchor or the question TXT source.

# 6. Required Metadata Resolution Upgrade

This is the second and more important Knowledge Index requirement.

The intended metadata hierarchy is:

## Global Metadata Has a Value

If a file contains:

```text
Topic| History
SubTopic|
Level| 10
```

then the global values are authoritative.

For each metadata field independently:

```text
Global value exists
        ↓
Use global value
        ↓
Ignore individual-question value
```

Therefore:

**Global metadata overrides individual metadata.**

---

## Global Metadata Is Blank

If the file contains:

```text
Topic|
SubTopic|
Level|
```

then the engine must inspect individual question metadata where available.

For example:

```text
Global:
Topic|
SubTopic|
Level|

Question 1:
Topic| History
SubTopic| Ancient India
Level| 10

Question 2:
Topic| Geography
SubTopic| Physical Geography
Level| 12
```

The effective metadata is question-specific.

---

## Metadata Resolution Must Be Per Field

This is important.

The fallback is not all-or-nothing.

Example:

```text
Global:
Topic| History
SubTopic|
Level| 10

Individual:
Topic| Geography
SubTopic| Ancient India
Level| 12
```

Effective metadata:

```text
Topic    → History       ← global wins
SubTopic → Ancient India ← global blank, use individual
Level    → 10            ← global wins
```

Therefore each metadata field independently follows:

```text
                 Metadata Resolution
                         │
              ┌──────────┴──────────┐
              │                     │
       Global value exists?    Global blank?
              │                     │
             YES                   YES
              │                     │
       Use global value       Check individual
       Ignore individual      question metadata
                                    │
                              Available?
                               /       \
                             YES        NO
                              │          │
                       Use individual   Blank
```

This rule applies at minimum to:

```text
Topic
SubTopic
Level
```

and should be preserved as the project metadata inheritance principle.

---

# 7. Important Current Limitation in `questionLibraryEngine.js`

The current engine stops global metadata scanning when it encounters the first:

```text
Q|
```

or:

```text
QEN|
```

question marker.

After the first question marker, later metadata is ignored by the current global metadata extractor.

That behavior is acceptable only for the existing file-level metadata model.

The engine must therefore be upgraded so that it can properly support the project's intended metadata inheritance model:

```text
Global metadata
        ↓
Question-level fallback only where global is blank
```

The upgrade must not break the existing global metadata behavior.

---

# 8. File-Level vs Question-Level Metadata — Required Design

The intended model is:

### File-level metadata

```text
Global metadata
      ↓
Applies to all questions
```

when a value exists.

### Question-level metadata

```text
Individual question metadata
      ↓
Used only when the corresponding global field is blank
```

This means the parser should not unnecessarily inspect individual metadata when the global value is already authoritative.

This is both an architectural rule and a performance consideration.

# 9. Admin Portal — Required Future Upgrade

The current Admin Portal shows aggregate section totals but does not yet expose Topic/Sub-Topic question counts.

The desired behavior is hierarchical and interactive:

```text
GACA — total
│

│   ├── Sub-Topic A — count
│   └── Sub-Topic B — count
│
├── Topic B — count
│   └── Sub-Topic C — count
│
└── Topic C — count
```

### UI behavior

A Topic should be expandable/collapsible.

Example:

```text
GACA
  ▼ History ........ 180
      Ancient India .... 70
      Medieval India ... 55
      Modern India ..... 55

  ▶ Geography ........ 150

  ▶ Current Affairs .. 370
```

The Admin Portal should use the same generated Knowledge Index rather than creating a second statistics source.
